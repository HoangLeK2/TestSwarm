# Swarmote Research

Date: 2026-08-13

## Summary

Swarmote is a cloud Android phone platform for operating multiple isolated mobile profiles. It is closer to GeeLark, VMOS Cloud Phone, Redfinger, LDCloud, or MaxCloudPhone than to a local real-phone farm.

The product combines:

- Cloud Android profiles with persisted app state.
- Device fingerprint and environment management.
- Proxy inventory and proxy health checks.
- App/APK deployment.
- Asset/material management.
- Automation templates, custom scripts, visual flows, task scheduling, and task logs.
- Team roles, device group permissions, and billing controls.

For `device-farm`, Swarmote is useful as a product and architecture reference, not as a drop-in replacement. The current repo is oriented around real devices, relay, ADB/U2, XML hierarchy, and live phone control. Swarmote appears to provide hosted/virtual cloud phones and its own cloud control plane.

## Evidence

Official positioning from the public site and indexed descriptions:

- `https://www.swarmote.com/` positions Swarmote as secure cloud Android phones for managing multiple social media accounts.
- The public page loads a SPA with modules for cloud phone control, equipment/profile management, proxy, groups, apps, materials, scripts, task scheduling, logs, billing, and team/staff management.
- Similarweb indexes Swarmote with the same public positioning and compares it with other cloud-phone sites.

Frontend bundle inspection from the official site showed these concrete modules and API surfaces:

- Cloud phone control loads `ArmcloudEngine` and uses an Armcloud endpoint fallback: `https://openapi-hk.armcloud.net`.
- Device/profile APIs include list, open, close, token, state check, create, batch create, update, delete, reset/new equipment, transfer, pod info, and ADB info.
- Automation assets include script list, script info, user script list, script feedback, task schedule, task detail, task records, create task, and task controller modules.
- Pricing assets include free, pro, enterprise, concurrency, monthly device, and time-pack billing concepts.

## Product Model

Swarmote's main unit is a Profile, which represents an independent cloud mobile phone. The public docs describe these states:

- `Dormant`: cloud phone is sleeping; app data, login state, proxy IP, and cookies are sealed in cloud storage; no running cost.
- `Running`: profile is activated through concurrency quota, monthly device, or time-pack minutes.
- `Close`: profile syncs data and returns to dormant state.

This lifecycle is important because it separates account state from active compute. A user can create many profiles but only run a limited number concurrently.

## Billing Model

Observed public pricing config:

- Free: `$0/month`, basic environment creation/management, proxy management, automation, operation logs, AI assistant, 2 environments or 60 minutes, 1 seat.
- Pro: flexible plan, concurrency option, bonus environments, advanced environment features, batch creation, transfer, unlimited free members, and priority access. Public pricing text includes `From $2.99/device/mo`.
- Enterprise: custom plan for `10,000+` profiles and custom features.
- Time packs are sold by minute packages, from 2,000 minutes to 1,000,000 minutes.

The docs describe billing priority as free/gifted time, then time pack, then wallet. Running time can be capped daily for pay-as-you-go usage.

## Automation Model

Swarmote's automation model appears to include:

- Preset scripts/templates by platform.
- Custom visual flow designer.
- Action nodes such as click/input.
- Loop nodes.
- Scheduled tasks.
- Daily tasks.
- Interval tasks.
- Task monitoring and task logs.

This matches the direction already used in `device-farm`: explicit scenario nodes, loop nodes, UI hierarchy/XML based actions, and runtime logs. The main difference is infrastructure: Swarmote schedules cloud phone profiles; `device-farm` schedules physical devices and relay-controlled sessions.

## Architecture Inference

Likely architecture from public frontend assets:

```text
Web/Desktop Client
  -> Swarmote backend user/* APIs
  -> profile/equipment/task/proxy/app/material/billing services
  -> Armcloud RTC/control layer
  -> hosted Android cloud phone profile
```

Core domain objects:

- Profile/Equipment
- Device group/tag
- Proxy
- App/APK
- Material/asset
- Script/template
- Task/run
- Billing wallet/time pack/concurrency
- Team/member/role
- Operation log

## Comparison With Device Farm

Swarmote strengths:

- Cloud-phone onboarding is simple for users.
- Profile state is persistent and independent from runtime slots.
- Billing/resource model is clear: many profiles, limited running concurrency.
- Proxy management is first-class.
- App and material centers are integrated with automation.
- Team permissions and logs are productized.

Swarmote weaknesses or unknowns:

- No stable public API documentation was found during this pass.
- Frontend-minified API endpoints are not a reliable integration contract.
- Hosted/virtual Android can be detected by app integrity, SafetyNet, Play Integrity, virtualization checks, or behavior signals.
- Users must trust the vendor with account sessions, app data, assets, and proxy configuration.
- Latency, region quality, and proxy quality are vendor-dependent.

`device-farm` strengths:

- Real devices are controlled directly.
- ADB/U2/XML hierarchy gives deterministic node-level actions.
- Runtime can be deeply instrumented.
- Account/device/proxy policy can be owned locally.
- Lower vendor lock-in.

`device-farm` weaknesses:

- More operational complexity.
- Needs stronger productized scheduling, quotas, task logs, profile lifecycle, and proxy UX.
- Scaling requires physical device health, relay health, stream health, and account session health.

## Lessons To Borrow

These patterns are worth borrowing:

1. Treat account runtime as a Profile/Workspace, not only as a raw device session.
2. Separate persisted account state from active execution slots.
3. Add clear states: `dormant`, `starting`, `running`, `closing`, `failed`.
4. Add concurrency slots for long-running campaigns instead of letting campaigns fan out without a visible resource model.
5. Make proxy inventory and proxy health visible beside account/device state.
6. Keep app install and asset/material libraries as reusable campaign inputs.
7. Support scheduled, daily, interval, and duration-based tasks.
8. Show run counters directly: cycles, matched targets, actions taken, skipped items, errors, and last UI/XML snapshot.
9. Keep automation node contracts explicit and platform-agnostic.
10. Prefer U2/XML node actions over feedback-coordinate clicks for app automation.

## Risks

Do not blindly copy the anti-detect or mass-automation marketing language. For a production device automation system, the safer requirements are:

- Account and platform compliance controls.
- Rate limits and per-account quotas.
- Human-reviewable action logs.
- Clear stop conditions.
- Secrets stored in account storage, not scenario variables.
- No hardcoded platform-specific behavior inside generic scenario nodes.
- No coordinate-only fallback unless the action is explicitly marked best-effort.

## Recommendation

Use Swarmote as a reference for product structure:

- Profile/workspace lifecycle.
- Concurrency-based scheduler.
- Proxy/app/material centers.
- Automation templates plus visual custom flows.
- Task monitor and operation logs.
- Team permissions by device group.

Do not replace the current real-phone architecture with cloud phones unless the product explicitly wants a hosted virtual-phone business model. For the current system, the better path is to keep U2/ADB real-phone control and bring Swarmote-like resource management, profile lifecycle, task scheduling, and observability into `device-farm`.
